# 交接：未真机验证功能（2026-10-24）

本文件记录 **v0.2.22 / v0.2.23** 新增、但尚未由真机操作验证的功能。
接手时不要把它们当成“已经可用”，按下面的检查表逐项测。

验证层级约定：

- **编译通过**：HAP 构建成功，仅能说明语法/链接没有问题。
- **qemu 跑通**：native 纯逻辑在 qemu 下跑过，不代表 ArkUI/设备行为。
- **真机跑通**：必须在 HarmonyOS 设备上实际操作确认。

## 1. 特效标签 UI（v0.2.22）

### 位置与行为

- 模式行：`台词 / 样式 / 视频 / 音频 / 特效 / 日志 / 缓存`
- 文件：`app/entry/src/main/ets/pages/Editor.ets`
  - `insertEffect()`
  - `showEffects` 分支
- 支持插入：

| UI | 生成标签 |
|---|---|
| 位置 | `\pos(x,y)` |
| 移动 | `\move(x1,y1,x2,y2,t1,t2)` |
| 淡入淡出 | `\fad(in,out)` |
| 旋转 | `\frz(deg)` |
| 缩放 | `\fscx(s)\fscy(s)` |
| 模糊 | `\blur(radius)` |

- 插入位置固定为 **当前行开头**，生成独立覆盖块：
  `{\tag}原文本`
- 插入后自动回到“台词”页，仍需点 **应用** 才会写入事件。
- 空输入使用默认值：位置 `0,0`；移动时间 `0,2000`；淡入淡出 `200,200`；
  缩放 `100`；模糊 `2`。

### 尚未验证

- 没有在真机上实际插入并看 libass 预览。
- 没有验证 `\move` 的时间单位/顺序在 libass 下是否符合预期。
- 没有验证 `\fad` 在视频/音频预览中的实际效果。
- 没有验证插入后切换行、Apply、保存/导出是否保持。
- 没有验证重复插入同一特效时的覆盖行为。

### 已知限制

- **只插入到行首**，不能对选中片段插入特效。
- **不做同标签替换**：再次插入不同参数的 `\pos` 会在行首再加一个独立块；
  ASS 多覆盖块的取值行为需要真机/上游确认。后续应实现“同标签替换”。
- 没有坐标预览/画布，用户只能手填像素坐标。
- 没有 `\clip / \t / \fade / \org` 等更复杂标签。

### 真机验收清单

1. 选中一行，特效页填 `320,180`，插入 `\pos`；
2. 回台词页，确认行首出现 `{\pos(320,180)}`；
3. 点应用，libass 预览确认位置变化；
4. 保存/导出，重新打开确认标签未丢；
5. 再插入 `\fad(200,200)`，确认两个覆盖块可共存；
6. 重复插入同参数 `\pos`，确认不会产生难以解释的重复块；
7. 切换上一行/下一行，确认不会把特效写到别的行。

## 2. 异步波形解码（v0.2.23）

### 实现方式

- native：`app/entry/src/main/cpp/napi_init.cpp`
  - `WaveformWorkData`
  - `WaveformExecute`（worker 线程，禁止调用 NAPI）
  - `WaveformComplete`（EventLoop 线程，`napi_resolve_deferred`）
  - `StartWaveformWork()`
  - `waveformAsync(path,buckets)`：WAV PCM
  - `videoWaveformAsync(path,buckets)`：容器音轨（最小 ffmpeg）
- ArkTS：`Editor.ets`
  - `parseWaveform()` 改为 `async`，`await aegisub.waveformAsync(...)`
  - `parseVideoWaveform()` 使用 `videoWaveformAsync`
  - `waveformRequest` / `videoWaveformRequest` 防止旧请求覆盖新文件
- 官方文档依据：
  - [Asynchronous Task Development Using Node-API](https://developer.huawei.com/consumer/en/doc/harmonyos-guides-V13/use-napi-asynchronous-task-V13#example-promise)
  - [Node-API 异步操作/Promise](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/use-napi-about-promise)
- 关键约束（文档明确）：
  - `execute` 在 worker 线程执行，**不能调用 NAPI**；
  - `complete` 在 EventLoop 线程执行，才能 resolve/reject；
  - 结果通过 `napi_deferred` 跨线程传递。

### 尚未验证

- 没有真机验证“选长视频/长音频时 UI 不冻结”。
- 没有验证解码期间切换页面、换文件、清缓存时的请求竞态。
- 没有验证连续快速选择多个文件（旧请求是否被正确丢弃）。
- 没有验证异步解码和 AVPlayer/Video 同时读文件的并发行为。
- 没有验证 HAP 在 worker 池线程中调用最小 ffmpeg 的线程安全（理论上每个 job 独立上下文）。

### 真机验收清单

1. 选一个 30 分钟以上、或至少 5 分钟的视频/音频，观察选择后界面是否还能响应；
2. 解码期间切到别的模式再回来，确认不崩、状态正确；
3. 解码未完成时再选另一个文件，确认最终波形属于后选文件；
4. 解码未完成时清音频/视频缓存，确认不崩、旧结果不覆盖；
5. 解码完成后播放、缩放、Slider 定位正常；
6. 同时打开视频音轨波形和音频波形，确认互不覆盖。

### 可能的风险

- Native worker 同时跑两个 FFmpeg/文件读取，低内存设备可能变慢；
  必要时加串行队列或限制并发。
- ArkTS 页面销毁后 Promise 仍会 resolve；当前只更新组件状态，未做页面生命周期取消。
- 若设备 NAPI worker 池很小，连续多次请求可能排队；UI 不冻结但波形出现会延迟。
