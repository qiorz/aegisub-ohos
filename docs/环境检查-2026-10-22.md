# Aegisub → HarmonyOS 环境检查（2026-10-22）

目的：在拉源码、定方案之前，确认本机工具链、构建通道、依赖存量与硬约束。
本文所有结论都标注验证层级：**编译通过 / qemu 跑通 / 真机跑通**，三者不混用。

## 〇、结论摘要

| 项目 | 结论 | 验证层级 |
|---|---|---|
| HarmonyOS CLT 26.0.0 / SDK API 26 | 可用，但**非交互 shell 必须 source** | 编译通过 |
| hvigorw 打 HAP | 正常，样例工程 19.7 s，产物 unsigned HAP | 编译通过 |
| OHOS clang 交叉编译 C/C++（静态） | 正常，C++20 / thread / regex / locale 均通过 | qemu 跑通 |
| CMake / Meson 交叉编译 | 两条通道都通过，产物可被 qemu 执行 | qemu 跑通 |
| 动态链接产物 + qemu | **不可用**，加 `-L /opt/ohos-run` 仍段错误 | qemu 失败 |
| 真机 | **未连接**，`hdc list targets` 为空 | 未验证 |
| 签名 | p12 + CSR 就绪，缺 AGC 签发的 `.cer` / `.p7b` | 未出签名包 |
| 上游源码 | 已迁到 `TypesettingTools/Aegisub`，最新 v3.5.1（Meson） | git 可拉取 |
| **最大阻塞** | **wxWidgets GUI（std/stc/gl）在 OHOS 无原生后端** | 方案风险 |

一句话：**工具链和 HAP 流水线没问题；Aegisub 的核心库（libaegisub）有可行路径；
但完整 GUI 不是“编译一下”能解决的，wxWidgets 缺 OHOS 后端是硬阻塞。**

### 2.2 发现的 PATH 问题（重要）

`/etc/profile.d/harmonyos.sh` 只被登录 shell / `.bashrc` 加载。工具调用走的是
`bash -c`（非交互），因此默认 `PATH` 里**没有** `hvigorw` / `ohpm` / `hdc`：

```bash
$ bash -c 'command -v hvigorw ohpm hdc cmake'   # 全部 MISSING
```

显式 source 后正常：

```bash
$ source /etc/profile.d/harmonyos.sh
$ command -v hvigorw ohpm hdc
/opt/harmony26/command-line-tools/bin/hvigorw
/opt/harmony26/command-line-tools/bin/ohpm
/opt/harmony26/command-line-tools/sdk/default/openharmony/toolchains/hdc
$ hdc -v
Ver: 3.2.0f
```

另外 NDK 的 cmake **没有**进 PATH（只加了 `toolchains`）。本工作区已提供
`scripts/env.sh`，一次性补齐：

```bash
source scripts/env.sh
# 之后 hvigorw / ohpm / hdc / cmake / OHOS_CC / OHOS_CXX 均可用
```

### 2.3 宿主机构建依赖

已具备：`gcc/g++ 12.2`、`make`、`ninja 1.11`、`meson 1.0.1`、`autoconf/automake`、
`libtoolize`、`pkg-config`、`python3 3.11`、`qemu-aarch64-static 7.2`、`JDK 17`。

缺失（按对 Aegisub 的影响排序）：

| 缺失 | 是否阻塞 | 说明 |
|---|---|---|
| `cmake`（系统 PATH） | 否 | NDK 自带 3.28，`scripts/env.sh` 已加入 PATH |
| `msgfmt` / `intltool` | 否 | 只影响翻译 `.mo` 生成；可先关翻译 |
| `zip` | 否 | hvigor 打包自带实现 |
| `bison` / `flex` | 否 | 上游已有生成好的 parser |
| `nasm` / `yasm` | 否 | 仅 x86 SIMD；aarch64 交叉用不到 |
| `libtool` 二进制 | 否 | `libtoolize` 在；autotools 足够 |

apt 源可用（阿里云镜像），上述包均可 `apt-get install`，合计约 100–200 MiB。

## 三、构建通道验证

### 3.1 HAP 流水线（编译通过）

复制样例工程到 `/tmp` 构建，避免污染 HandBrake 工作区：

```bash
source /etc/profile.d/harmonyos.sh
cp -a /root/opt/dsh/workspace/hello-harmony /tmp/hello-test
cd /tmp/hello-test
hvigorw --mode module -p product=default -p module=entry@default assembleHap --no-daemon
```

结果：`BUILD SUCCESSFUL in 19 s 702 ms`，34 tasks，产物
`entry/build/default/outputs/default/entry-default-unsigned.hap`。
未配置签名，`SignHap` 被跳过——符合预期。

### 3.2 CMake 交叉编译（qemu 跑通）

```bash
source scripts/env.sh
cmake -S . -B b -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=$OHOS_TOOLCHAIN_FILE \
  -DOHOS_ARCH=arm64-v8a -DCMAKE_BUILD_TYPE=Release
cmake --build b
qemu-aarch64-static ./b/smoke
```

结果：编译、链接、qemu 执行均通过（`cmake-ohos-ok`）。
唯一 warning 是 `--gcc-toolchain=...` 未使用，无害。

### 3.3 Meson 交叉编译（qemu 跑通）

Aegisub 3.4+ 用 Meson，这条通道必须通。交叉文件核心：

```ini
[binaries]
c = '.../aarch64-unknown-linux-ohos-clang'
cpp = '.../aarch64-unknown-linux-ohos-clang++'
ar = '.../llvm-ar'
strip = '.../llvm-strip'
pkg-config = 'pkg-config'
[host_machine]
system = 'ohos'
cpu_family = 'aarch64'
cpu = 'aarch64'
endian = 'little'
```

结果：`meson setup` / `compile` / qemu 执行全部通过（`meson-ohos-ok`）。
注意 `host_machine.system()` 会是 `ohos`（不是 `linux`），
Aegisub 的 luajit 等子项目需要显式映射（外部适配记录里写作 `harmonyos`，两者都要兼容）。

### 3.4 静态 vs 动态（qemu）

```bash
$OHOS_CC --target=aarch64-linux-ohos -static hello.c -o hello-static
qemu-aarch64-static ./hello-static          # OK: ohos-ok static

$OHOS_CC --target=aarch64-linux-ohos -O2 hello.c -o hello-dyn
qemu-aarch64-static -L /opt/ohos-run ./hello-dyn
# Segmentation fault (exit 139)
```

补充验证：`-no-pie` 动态产物、显式 `ld-musl-aarch64.so.1 --library-path`
均仍然段错误。`/opt/ohos-run/lib` 有 139 个 OHOS 库和 musl loader，
但**不足以让动态产物在 qemu 7.2 下跑起来**；根因未完全定位（musl/qemu 版本或
TLS/reloc 差异）。结论与旧文档一致：**本地验证只走 `-static`**。

### 3.5 C++ 能力（qemu 跑通）

用 `-static -std=c++17` 编译并运行了包含 `std::thread`、`std::regex`、
`std::locale`、`std::vector` 的测试，输出 `thread-ok` / `cpp-ok 2 1`。
说明 OHOS clang 15 + libc++ 的 C++20 基础能力可用（Aegisub 3.5.1 要求 C++20）。

## 四、上游源码与版本

### 4.1 上游已迁移

- 旧地址 `Aegisub/Aegisub` 的 master 停在 **v3.2.2-migrated**（autotools）。
- 当前官方仓库是 **`https://github.com/TypesettingTools/Aegisub`**，
  最新 tag：**v3.5.1**，构建系统 **Meson**，`cpp_std=c++20`。
- v3.4.2 是外部 OHOS 适配记录使用的版本；v3.5.1 是最新稳定 tag。

```bash
$ git ls-remote --tags https://github.com/TypesettingTools/Aegisub.git | tail
... refs/tags/v3.4.2
... refs/tags/v3.5.0
... refs/tags/v3.5.0-beta
... refs/tags/v3.5.1
```

### 4.2 现代版本的依赖（meson.build 实测）

必需：

- `fontconfig`（非 Windows/macOS 强制）
- `iconv`（有 fallback 子项目）
- `libass >= 0.9.7`（有 fallback）
- `boost >= 1.70`：**chrono、locale**（静态时还要 thread；<1.77 还要 regex）
- `zlib`
- `wxWidgets >= 3.2.2`，模块 **std / stc / gl**
- `icu-uc`、`icu-i18n >= 4.8.1.1`
- OpenGL（`GL/gl.h` 或 `dep_gl`）
- `luajit >= 2.0`（默认内置子项目）
- 音频：PulseAudio / ALSA / PortAudio / OpenAL（至少一个，否则只能无声）
- 视频：`ffms2 >= 2.22`（默认子项目）
- 可选：`fftw3`、`hunspell`、`uchardet`、`libcurl`、`libportal`、`csri`

Meson `subprojects/` 自带 ffmpeg / ffms2 / libass / freetype / fribidi / harfbuzz /
boost / icu / luajit / curl / expat / gtest 的 wrap，能 fallback 全源码构建，
但本机内存/磁盘**扛不住全量**，应尽量用系统/预编译库并关掉不必要 fallback。

### 4.3 GUI 耦合度（关键数字）

```bash
$ grep -rl '#include <wx/' src | wc -l
161
$ ls src/*.cpp | wc -l
302
$ ls src/dialog* | wc -l
41
```

`libaegisub/` 里 **0** 个文件直接 include wx 头；只在 `format.h` 前向声明 `wxString`
并为它保留模板特化（`charset_conv.cpp` 仅注释提及）。实际是否需要链接 wxBase，
要在第一次 Meson setup 时验证；外部适配记录选择的是 wxBase（`wx-baseu-3.2`）。
GUI 全部在 `src/`。
这与外部适配记录一致：libaegisub 只需 wxBase（`wx-baseu-3.2`），
GUI 前端才需要 std/stc/gl。

## 五、可复用依赖盘点

### 5.1 HandBrake 已有（AArch64 OHOS）

| 库 | 路径 | 版本 | 备注 |
|---|---|---|---|
| libass | `hb-build/deps/libass-0.17.4/libass/.libs/libass.a` | 0.17.4 | **CONFIG_FONTCONFIG 未开** |
| freetype | `hb-build/deps/freetype-VER-2-13-3/cbuild/libfreetype.a` | 2.13.3 | 静态，AArch64 |
| fribidi | `hb-build/deps/fribidi-1.0.16/_b/lib/libfribidi.a` | 1.0.16 | 静态 |
| harfbuzz | `hb-build/deps/harfbuzz-8.5.0/_b/src/libharfbuzz.a` | 8.5.0 | 静态 |
| ffmpeg | `hb-port/src/prebuilt/lib/libav*.a` | 8.x | 静态，AArch64 |
| lame / x264 / x265 / jpeg 等 | 同上 | — | 与本项目关系不大 |

ABI 核对：`llvm-readelf -h` 显示 `Class: ELF64`、`Machine: AArch64`，可复用。

**注意**：libass 的 `config.h` 里 `CONFIG_FONTCONFIG` 是 `#undef`。
Aegisub 的 libass provider 用 `ass_set_fonts(..., "Sans", 1, ...)`（AUTODETECT），
没有 fontconfig 时字体匹配会退化。要么给 libass 重编开 fontconfig，要么
改成显式 font provider。这是后续必须处理的一项。

### 5.2 OHOS sysroot 自带

- `libEGL.so` / `libGLESv2.so` / `libGLv4.so`、`GLES2/GLES3/EGL` 头文件
- `libace_napi.z.so`、`libace_ndk.z.so`、`napi` 头
- `native_window` / `external_window.h`、`xcomponent` 头
- `libohaudio.so` + `ohaudio` / `ohaudiosuite` 头（音频后端可接 OHAudio）
- `libicu.so`（**ICU 72.1，合并库**），有 `unicode/` 头，但**没有 `icu-uc.pc` / `icu-i18n.pc`**
- `libz.so` + `zlib.h`
- **没有** fontconfig、freetype、harfbuzz、curl、fftw、hunspell 的 dev 文件

### 5.3 需要新增构建/补齐

| 依赖 | 方案 | 预估 |
|---|---|---|
| Boost 1.83（chrono/locale/thread/regex） | 用 wrap 源码，`b2` 只编需要的库；或 header-only + 手工编 locale | 中，内存敏感 |
| ICU | 复用 sysroot `libicu.so` 72.1，伪造 `icu-uc/icu-i18n` 的 `.pc` 和 `libicuuc.so` 等符号链接；或源码编 | 小（复用）/ 大（源码） |
| fontconfig | 源码交叉编（依赖 freetype、expat），fonts.conf 指向 `/system/fonts` | 小 |
| fftw3 | 可选；Aegisub 音频频谱用，可先关 | 小 |
| hunspell / uchardet | 可选，可先关 | 小 |
| libcurl | 更新检查用，可关 | 小 |
| luajit | 用子项目，补 `ohos`/`harmonyos` 平台映射 | 小（已知补丁） |
| ffms2 | 对 HandBrake 的 ffmpeg 静态库编 | 中 |
| wxWidgets | **无 OHOS 后端**，见下 | **极大** |
| 音频后端 | 新写 OHAudio backend（约数百行） | 中 |
| 视频输出 | wxGLCanvas 在 OHOS 不存在；需 XComponent + EGL/GLES 自绘 | 大 |

## 六、硬阻塞与风险

### 6.1 wxWidgets GUI（最大风险，未解决）

- Aegisub GUI 的 161 个文件依赖 wx；需要 `std`（基础控件）、`stc`（Scintilla 编辑器）、
  `gl`（视频预览）。
- wxWidgets 官方没有 OHOS 原生后端。外部公开记录中，wxWidgets 3.3.3 的
  “HarmonyOS PC 适配”实际交付的是 **wxUSE_GUI=OFF 的 wxBase**；
  另一个 GUI 验证是 **GTK3 Broadway**（HTML5 后端，跑在签名 HAP 里），
  明确不是 HarmonyOS 原生窗口后端。
- 因此完整 GUI 只有几条路：
  1. **写 wxWidgets OHOS 后端**（XComponent/ArkUI 原生窗口 + EGL + 输入 + 控件绘制）。
     工作量最大，但最贴近“保持上游功能”。
  2. **ArkUI 重写 GUI**，libaegisub 通过 NAPI 暴露。原生体验最好，但要重写 41 个对话框
     和主界面、时间轴、音频/视频预览，工作量同样巨大。
  3. **GTK3 + Broadway + WebView** 兼容层。能较快跑起界面，但不是原生、GL 视频预览受限、
     依赖 WebSocket/WebView，产品化风险高。
  4. **X11/Wayland 兼容层**（若目标设备是 HarmonyOS PC 且系统提供）。目前没有本机证据。

### 6.2 fontconfig

Aegisub 非 Windows/macOS 路径强制 fontconfig；OHOS 没有。需要：
- 交叉编 fontconfig（freetype + expat），
- 配置 `FONTCONFIG_PATH` / `fonts.conf` 指向 `/system/fonts`，
- 决定 libass 是否重编开 fontconfig。

### 6.3 音频/视频

- OHOS 没有 ALSA/OpenAL/PortAudio/PulseAudio/OSS；Meson 至少要一个音频后端，
  否则 configure 会失败或只能静音。需写 OHAudio backend。
- 视频预览走 `wxGLCanvas` + `video_out_gl.cpp`；OHOS 上要换成
  XComponent + EGL/GLES（或先关视频预览）。

### 6.4 环境/流程

- **真机未连接**：`hdc list targets` 为 `[Empty]`；目前只能到 qemu（静态）级别。
- **签名未闭环**：`/opt/harmony-signing/app.p12`（alias `harmony-app`）和 CSR 正常，
  但缺 AGC 签发的 `.cer` 与 debug `.p7b`，暂时只能出 unsigned HAP。
- **GitHub raw 被重置**：`raw.githubusercontent.com` 连接被 reset；
  `git clone` / `git ls-remote` 正常。拉源码用 git，不要依赖 raw 单文件。
- **内存**：编译大文件时 `-j2` 也可能触发 OOM；建议 `-j1`，并用 `free -h` 观察 swap。
